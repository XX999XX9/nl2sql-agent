## 1. 评测日志 / 提示词工作台：前端明文口令改为后端加密校验

### 问题

原先 `auth.js` 里硬编码 `LOGS_PASSWORD = "666"`，由浏览器判断口令后写一个 sessionStorage 标记放行。
这带来三个问题：

1. 口令进入前端源码与浏览器缓存，任何人打开 DevTools 就能看到；
2. “是否通过校验”由客户端决定，直接改 sessionStorage 即可绕过；
3. 后端接口（`/api/eval/runs`、`/api/prompt_optimize/*`）本身没有任何鉴权，知道 URL 就能直接拉取评测明细与提示词内容。

### 实现方式

新增 [eval_access.py](../backend/app/api/eval_access.py)，把口令校验与访问凭证都放到服务端：

1. **口令校验**：`POST /api/eval/auth` 收到口令后，用 `hmac.compare_digest` 做常量时间比较（避免逐字符比较带来的时序侧信道），口令来源为 `NL2SQL_EVAL_PASSWORD`，默认 `666`。
2. **签发令牌**：校验通过后签发 `过期时间戳.HMAC-SHA256 签名` 形式的无状态令牌，密钥来自 `NL2SQL_EVAL_SECRET`（未配置则进程启动时随机生成），有效期 `NL2SQL_EVAL_TOKEN_TTL` 默认 7200 秒。
3. **接口鉴权**：把令牌放在 `X-Eval-Token` 请求头，FastAPI 依赖 `require_eval_access` 负责校验——先判过期，再用 `compare_digest` 比对签名，失败直接 401。
4. **路由接入**：
   - [eval_logs.py](../backend/app/api/routes/eval_logs.py#L190-L197) 新增 `/auth` 接口；
   - `/runs` 与 `/run`（单次运行详情）增加 `Depends(require_eval_access)`；
   - [prompt_optimize.py](../backend/app/api/routes/prompt_optimize.py#L21) 用**路由级依赖**统一保护，避免逐个接口漏加；提示词优化属于内部工具，整组不对外开放。

### 为什么用 HMAC 无状态令牌，而不是服务端 session 或 JWT 库

- 评测页是低频内部工具，不值得为它引入会话表或额外依赖；
- 无状态令牌天然适配多进程/多 worker（只要密钥一致），也不用清理过期会话；
- 只签名“过期时间”这一个字段，攻击面最小：令牌不能携带任何可被篡改的权限信息。

### 前端配合

- [auth.js](../frontend/static/js/auth.js)：删除明文口令常量，改为 `fetch("/api/eval/auth")` 提交口令；成功后只保存 `token + 过期时间` 到 `sessionStorage`；`evalToken()` 每次读取都检查过期，过期即清除。
- [api.js](../frontend/static/js/api.js)：统一在 `authHeaders()` 里附加 `X-Eval-Token`。
- [eval_logs.js](../frontend/static/js/eval_logs.js)：自带 `api()` 同样带令牌，遇 401 清令牌并刷新页面重新验证。
- [prompt_optimize.html](../frontend/prompt_optimize.html)：页面脚本不再直接引入，改为口令门通过后由 `auth.js` 按 `data-auth-script` 动态加载，未通过时工作台代码根本不下发。

### 验证

- `python -m py_compile` 通过；
- 未带令牌访问 `/api/eval/runs` → 401；错误口令 `POST /api/eval/auth` → 401；正确口令 → 返回 `token/expires_in`，带令牌即可正常取数（需启动服务后人工确认）。

## 2. Docker 部署修复

### 问题

`docker-compose.yml` 里 backend 服务写了 `build: ./backend`，但仓库里**没有 Dockerfile**，`docker compose up --build` 直接失败；同时 compose 未把 `backend/.env` 的 LLM / MySQL 凭据注入容器，即使构建成功也会因缺少 Key 启动即报错。

### 实现方式

1. 新增 [backend/Dockerfile](../backend/Dockerfile)：
   - 基础镜像 `python:3.11-slim`；
   - 先装 `gcc/g++` 再 `pip install -r requirements.txt`（`chromadb`、`pymysql` 等存在需要编译的依赖，缺编译器会在构建期失败）；
   - `COPY . .` 后 `CMD ["python", "run.py"]`，与本地启动方式一致（端口仍由 `NL2SQL_PORT` 控制）。
2. 新增 [backend/.dockerignore](../backend/.dockerignore)：排除 `.env`、`__pycache__`、`data/`、`logs/` 等，避免把密钥与运行期产物打进镜像。
3. 修改 [docker-compose.yml](../docker-compose.yml)：
   - backend 增加 `env_file: ./backend/.env`，凭据以环境变量注入；
   - 增加 `NL2SQL_SERVE_FRONTEND=false`，前端交给 nginx 容器托管并反代 `/api`，后端不再重复挂载静态目录；
   - 保留 `config/prompts/data/logs` 目录挂载，配置与提示词可在容器外修改。
4. 更新 [README.md](../README.md#L248-L257) 的 Docker 段：补上“先准备 .env、`docker compose up -d --build`、访问入口”。

### 取舍说明

- 没做多阶段构建：本项目依赖以 wheel 为主，单阶段镜像体积可接受，多阶段会让构建脚本复杂度翻倍，收益有限；
- 没把 `.env` 打进镜像：密钥随镜像分发会产生“镜像即泄漏”的风险，`env_file` 是更合适的边界。

### 验证

本机 WSL 未安装 Docker CLI，无法实际构建；已用静态检查确认 compose 引用的 Dockerfile、`.dockerignore`、`.env` 均存在且路径正确。

## 3. SSE 断连后流水线不终止、运行状态停在 running

### 问题

前端关闭页面或网络中断时，客户端不再消费 SSE。Starlette 检测到断连后会取消“推送流”的任务，但：

- 同步生成器由 `iterate_in_threadpool` 消费，取消不会确定性地调用 `close()`；
- 生成器里 `GeneratorExit` 属于 `BaseException`，不会被 `except Exception` 捕获；
- 结果就是 `iter_run` 的收尾逻辑不执行，`finish_run` 没被调用，评测日志/运行目录里的状态长期停留在 `running`。

### 实现方式

1. [pipeline.py](../backend/app/nl2sql/pipeline.py#L436-L474) 在 `iter_run` 中增加 `finished` 标志：
   - 正常结束（`else`）或抛异常（`except Exception`）都置为 `True`；
   - `finally` 中若 `not finished`，说明是被外部关闭（断连），此时主动 `finish_run(status=error, error="执行被中断（客户端断开连接）")`，让运行状态确定收敛；收尾失败只记 warning，不影响其他逻辑。
2. [chat.py](../backend/app/api/routes/chat.py#L96-L117) 给 `StreamingResponse` 挂 `background=BackgroundTask(close_stream)`：
   - Starlette 在断连后会执行 background task，因此生成器会被**主动** `close()`，而不是等 GC 回收；
   - 关闭时会触发 `GeneratorExit`，走 `finally`，上面的收敛逻辑立即生效。
3. 处理并发关闭的竞态：生成器可能正在被消费线程执行（例如 LLM 请求中），此时 `close()` 抛 `ValueError: generator already executing`；`close_stream()` 捕获该异常并忽略，交由 `iter_run` 自身在下次产出/结束时收尾，避免后台任务抛错污染日志。
4. `_EMIT_BUFFER.reset(token)` 用 `try/except (ValueError, RuntimeError)` 包裹：跨线程关闭时 ContextVar 复位可能报错，但该上下文即将销毁，忽略即可。

### 为什么没改成 async 路由 + `request.is_disconnected()`

- Starlette 的 `StreamingResponse` 内部已在监听 `receive`，再调 `is_disconnected()` 会争抢同一个接收通道，反而可能阻塞；
- 改成 async 后需要用 `run_in_threadpool(next, gen)` 消费同步生成器，`ContextVar(_EMIT_BUFFER)` 的跨调用语义会变，存在破坏事件采集的风险；
- 当前方案保持同步路由不变，只增加“确定性关闭 + 收尾收敛”，改动面最小。

## 4. SQL 执行超时遗漏

### 问题

原先只有主查询 `execute()` 设置了 `SET SESSION max_execution_time`。以下旁路查询走裸连接，没有超时：

- `_count_total()`：截断时对整条查询包 `SELECT COUNT(*)`，大库上可能比主查询更慢；
- `explain()`：性能门禁每次都要跑；
- `table_indexes()`：查 `information_schema.STATISTICS`；
- 值链接器采样：`COUNT(DISTINCT)` / `DISTINCT` 是真实重查询；
- Schema 刷新：大库上 `COLUMNS` / `KEY_COLUMN_USAGE` 也可能变慢。

连接池会复用物理连接，一旦某个旁路查询长时间挂住，连接就被占住，后续请求只能等池子耗尽。

### 实现方式

1. [sql_executor.py](../backend/app/nl2sql/sql_executor.py#L57-L75) 抽出 `@contextmanager _connect()`：取连接后统一执行 `SET SESSION max_execution_time = execution_timeout * 1000`，再交给调用方使用。`execute` / `_count_total` / `explain` / `table_indexes` 全部改为走这个入口。
2. 超时设置本身也做降级：老版本 MySQL 不支持该变量时，捕获 `DBAPIError` 记 warning 后继续（不因“设不了超时”让整条链路不可用）。
3. [value_linker.py](../backend/app/nl2sql/value_linker.py#L87) 采样前同样设会话超时，避免 `COUNT(DISTINCT)` 把连接长期占住。
4. [schema_manager.py](../backend/app/nl2sql/schema_manager.py#L20) 刷新前同样设超时，保持全链路口径一致。

### 为什么用会话级 `max_execution_time` 而不是 `statement_timeout` / 线程 kill

- MySQL 8 的 `max_execution_time` 只作用于只读 SELECT，正好匹配本执行器的只读定位，不会误杀事务类语句；
- 不需要额外线程去 kill 连接，失败会以 `3024` 错误码返回，已有 `_classify_error` 归为 `timeout` 类别，可直接进入纠错链路。

## 5. SQLGuard 关键词表补充

### 问题

原关键词表覆盖了写操作、文件读写与 `information_schema` 访问，但漏掉了三类只读也能造成破坏的函数：

- 时间/资源型阻塞：`SLEEP()`、`BENCHMARK()`，可让单条查询长时间占用连接与 CPU；
- 命名锁：`GET_LOCK()` / `RELEASE_LOCK()`，只读查询也能留下全局锁影响其他会话；
- 报错注入：`UPDATEXML()` / `EXTRACTVALUE()`，常被用来把查询结果拼进错误信息带出数据。

### 实现方式

[sql_guard.py](../backend/app/nl2sql/sql_guard.py#L29-L40) 在 `FORBIDDEN_KEYWORDS` 中新增 6 个词。判定沿用原有两条规则：

- 词边界匹配（`\bsleep\b`），不会误伤 `sleep_duration` 这类列名；
- 先扫原文、再扫剥注释后的可执行体，注释里出现同样拦截（宁枉勿纵）。

关键词层只是粗筛，后面仍有 sqlglot AST 细筛（单语句、必须是 SELECT/UNION）兜底。

## 6. Redis 旧键清理

### 背景

检查点已切换到官方 `langgraph-checkpoint-redis`，键前缀为 `nl2sql_checkpoint*`。旧的自研实现留下的键不再被任何代码读取，属于纯占空间的历史残留。

### 清理范围与依据

先全量 `SCAN` 并逐个记录 type/TTL，确认无代码引用后再删除：

| 键模式 | 含义 | 处理 |
|---|---|---|
| `nl2sql:ckpt:*` / `nl2sql:writes:*` | 旧自研检查点与写入标记 | 删除（本次为 0 个） |
| `nl2sql:thr:*` / `nl2sql:threads` / `nl2sql:seq` | 旧线程注册表与序号 | 删除（各 1 个） |
| `nl2sql_test*` | 旧测试前缀（`ckpt/writes/thr/threads/seq`） | 删除（11 个） |
| `write_keys_zset:*` | 官方写入键 zset，但对应线程的检查点已不存在 | 删除（6 个孤儿） |
| `nl2sql:session*` / `nl2sql:run*` / `nl2sql:user*` | 当前索引层仍在使用的目录键 | **保留** |
| `hobby` / `t` | 非本项目数据 | **保留**（不越界删除） |

执行结果：删除 20 个键，dbsize 从 31 降到 11；剩余键全部为当前索引层数据或无关数据。

### 注意

切换官方检查点后，旧会话的检查点数据本身已不可读（键布局不兼容），本次清理只是把已经失效的残留一并移除；会话索引键保留，历史会话仍能出现在列表里，但正文为空属于预期行为。

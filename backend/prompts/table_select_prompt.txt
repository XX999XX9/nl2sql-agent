{schema_context}

【信息充分性判断（人工澄清）】
在筛选之前，先判断用户问题是否缺少无法从表结构/多轮上下文中推断的关键信息，例如：
- 时间范围不明确（如“这几天”“最近”“上个月左右”缺少确切起止）；
- 业务口径不明确（如“营收额”可能指下单金额/支付金额/退款后净额，且表中存在多个候选口径字段）；
- 指代对象不明确且多轮上下文也无法消解。
只有“不向用户确认就无法保证 SQL 语义正确”时才发起澄清；能通过表字段注释、枚举值或多轮上下文合理确定的，不要滥用澄清。
需要澄清时，输出必须是且只能是如下 JSON（不要代码块、不要解释）：
{{"need_clarification": true, "questions": ["需要向用户确认的具体问题1", "具体问题2"]}}
questions 用面向业务用户的通俗中文，一次最多 4 条，每条只问一个信息点，并可给出可选口径/示例供用户选择。

【筛选要求】（信息充分、无需澄清时适用）
1. 通读用户问题涉及的全部业务实体与条件，结合【表关联关系】判断 JOIN 路径上必须经过的表。
2. 把表分为两类输出：
   - needed：生成 SQL 确定需要的表（含 JOIN 中转表、过滤/分组/排序/聚合所依赖的表）。
   - maybe：可能需要但不能完全确定的表（如问题表述歧义、可能存在的同义表），仅列表名。
   - 不需要的表无需输出：系统会自动以候选表全集减去 needed、maybe 反推，禁止罗列其余表名。
3. 对每个 needed 表，只输出 use_columns：SELECT 输出、WHERE 条件、JOIN ON 键、
   GROUP BY、ORDER BY、聚合函数中确定会用到的字段（含 JOIN 必需的主键/外键）。
   - 只列会用到的字段，字段名逐字抄自【全库表结构】，禁止臆造；
   - 不要输出未使用字段：其余字段由系统根据表结构自动补全，无需你回抄。
4. 输出必须是且只能是一个 JSON 对象（不要代码块、不要解释、不要注释），格式：
{{"needed": [{{"table": "表名", "use_columns": ["字段1", "字段2"]}}], "maybe": ["表名"]}}
